<a id="intro"></a>
Довольно давно в C++ сложилось негласное разделение на прикладную разработку и написание библиотек. Для многих прикладных программистов принцип «я не злоупотребляю шаблонами» стал признаком рационального подхода. Эту популярную позицию можно назвать «шаблонным минимализмом». Долгое время я и сам её придерживался, сознательно избегая подходов, которые принято считать трудными в чтении и поддержке. Однако со временем стало ясно, что такой минимализм нередко мешает видеть по-настоящему удачные решения. 

Исследование этого арсенала — техник за пределами привычного прикладного минимума, от которых часто отказываются по привычке, — стало темой данного цикла. Для кого-то подобные решения уже давно часть стандартной практики, для других — неоправданная магия. Здесь не устанавливаются жесткие правила. Цель — разобрать анатомию приёмов и понять, при каких условиях цена их внедрения окупается на практике.

Последовательность техник в подборке такова, что сначала идут самые простые в освоении техники и связанные с предыдущими. Оценка простоты, конечно, субъективна. Но можно сказать, что техника, требующая меньше кода, — более проста. А синтаксис шаблонов, опирающийся на хорошо известный нешаблонный синтаксис, проще, чем освоение принципиально новых элементов языка. Поэтому, например, решения на основе концептов оцениваются как сложные.

Итак, начинаем с самого простого. Естественным образом оказалось, что первые такие техники связаны с сильными типами и перегрузкой функций.

<a id="preventing-confusion"></a>
## Типовая задача: контроль порядка параметров

Возьмём распространённый случай: функцию с несколькими параметрами одинакового типа. Например, расчет скорости по расстоянию и времени. В коде это может выглядеть так:

```cpp
constexpr double speed(double d, double t) {
    return d / t;
}
```

Проблема здесь в том, что для компилятора оба параметра — просто числа. При вызове легко ошибиться, и программа продолжит работать, выдавая неверный результат:

```cpp
void test() {
    double distance = 100.0;
    double time = 5.0;
    
    // Ошибка: перепутали порядок аргументов
    auto v = speed(time, distance); 
    
    // Компилятор не видит проблемы, логика нарушена.
}
```

Информация о том, что число означает именно «расстояние», существует только в голове разработчика — это знание остается на уровне «джентльменского соглашения» программиста с самим собой, в котором компилятор не участвует и не может гарантировать его соблюдение. Когда между объявлением переменных и точкой вызова лежат сотни строк кода или границы разных модулей, это знание легко теряется, а любая опечатка в порядке аргументов превращается в трудноуловимый баг. 

Ситуация, когда доменные понятия (расстояние, время) подменяются техническими типами (`double`), называется антипаттерном **Primitive Obsession** (одержимость примитивами). Способ сделать этот негласный договор явным — зафиксировать смысл данных в самой системе типов, переложив рутинную проверку на компилятор.

Псевдонимы типа вроде `using Meters = double` здесь не помогут — они лишь создают синоним, а не новый тип. Для компилятора это всё тот же `double`, и он всё так же позволит их перепутать. Чтобы получить по-настоящему разные сущности, нам нужны полноценные структуры:

```cpp
struct Meters {
    double value;
};

struct Seconds {
    double value;
};

// Теперь типы несут смысл. Порядок аргументов защищен на уровне компиляции.
constexpr double speed(Meters d, Seconds t) {
    return d.value / t.value;
}

void test() {
    auto v = speed(Meters{25.0}, Seconds{5.0});
    // speed(Seconds{5.0}, Meters{25.0}); // Ошибка компиляции!
}
```

> **Важное уточнение:** Хотя в примерах выше сильные типы используются как обёртки над `double`, суть техники заключается не в замене примитивов, а в обеспечении **различимости** (distinctness) типов для компилятора. Если функция принимает несколько идентичных по структуре аргументов, возникает та же проблема, что и с анонимными числами. Приёмы, основанные на сильных типах, позволяют сделать доменные понятия несовместимыми на уровне системы типов, даже если их внутреннее устройство одинаково.

C++ сегодня — это язык производительности и развитых библиотек. Поэтому вопрос о рантайм-эффекте любой обертки возникает закономерно. Ожидается, что простое оборачивание данных в структуру не замедляет код. Это утверждение кажется привычным, но теорию всегда полезно подтверждать практикой. Заглянем в ассемблер: это лучшая иллюстрация того, что современный компилятор видит сквозь наши обертки так же легко, как и просто обычные числа:

  Под «нулевой стоимостью» подразумевается идентичность машинного кода для `double` и `Meters` при включенных оптимизациях (`-O2`). Чтобы компилятор мог исключить накладные расходы, тип должен оставаться **тривиальным**:

  <ol>
    <li><b>Правило деструктора:</b> Не объявляйте пользовательский деструктор (даже пустой). Используйте <code>default</code> или доверьтесь компилятору. Это позволит передавать объект через регистры процессора, а не через память.</li>
    <li><b>Прозрачность:</b> Помечайте конструкторы и операторы как <code>constexpr</code> и <code>noexcept</code>. Это помогает компилятору «стирать» границы типов еще до генерации машинного кода.</li>
    <li><b>Об ABI и «бесплатности»:</b> Здесь есть технический нюанс. На <b>System V ABI</b> (Linux, macOS) структура с одним <code>double</code> передается напрямую в XMM-регистре — это честный zero-cost. В <b>Windows x64 ABI</b> правила строже: любая структура (даже из одного числа) передается через целочисленный регистр (RCX). <br><br><b>Вердикт:</b> На практике это не имеет значения. Во-первых, одна инструкция <code>movq</code> для перемещения данных в XMM-регистр стоит доли наносекунды. Во-вторых, сильные типы чаще всего используются в небольших функциях, которые компилятор <b>инлайнит</b> (встраивает). При инлайнинге границы вызова стираются, и любая разница в ABI исчезает. Безопасность кода стоит гораздо дороже, чем одна микроскопическая задержка процессора.</li>
  </ol>
</details>

<a id="scaling-up"></a>
## Возможности и области применения

Защита от перепутанных аргументов — лишь первая из задач, которые решают сильные типы. Опытные практики могут сразу возразить: не пальба ли это из пушки по воробьям, — обёртка над каждым параметром функции ради одной проверки? Это и есть тот самый вопрос баланса, к которому предстоит вернуться. Но прежде чем взвешивать цену, давайте посмотрим на другие возможности сильных типов — те, что делают их чем-то большим, чем просто «страховкой» при передаче параметров в функцию.

<a id="logic-protection"></a>
### Защита логики взаимодействия

Теперь, когда на вход функции попадают не безликие числа, а объекты разных классов, несущие конкретный смысл, появляется еще одна возможность — ограничить использование этих параметров уже внутри функции. 

Вместо того чтобы вручную следить за физическим смыслом каждой формулы, можно определить **роль** типа через набор разрешенных операций. В результате неверный код становится **невыразимым**: компилятор не просто «находит ошибку», он не находит способа собрать бессмысленное действие.

```cpp
struct Meters {
    double value;
    explicit constexpr Meters(double v) : value(v) {}
    explicit operator double() const { return value; }

    // Разрешаем только те действия, которые имеют смысл для этой сущности:
    Meters operator+(Meters other) const { return Meters{value + other.value}; }
    Meters operator-(Meters other) const { return Meters{value - other.value}; }
    
    // Любые другие взаимодействия (например, с Seconds) не прописаны, 
    // и компилятор заблокирует их автоматически.
};
```

Многим этот приём напомнит классическую инкапсуляцию, и это действительно так. Раз уж параметры стали объектами, появляется выбор: либо использовать их просто как контейнеры, каждый раз доставая значения через `.value`, либо описать правила их взаимодействия в самих типах. Во втором случае часть контроля за логикой берет на себя компилятор.

**Однако ручное описание таких правил для каждой новой сущности требует времени.** Как видно из примера с `Meters`, каждый оператор нужно прописывать явно. Если расчетов в проекте мало, а данные лишь передаются по цепочке вызовов без обработки, такая подготовка типов может привести к излишнему усложнению синтаксиса без реальной выгоды.

Чтобы почувствовать масштаб этой рутины, представьте, что вам нужно разграничить не две, а десятки сущностей: `Kilograms`, `Liters`, `Grams`… Для каждой структуры придется написать похожий блок:

```cpp
struct Kilograms {
    double v;
    Kilograms operator+(Kilograms o) const { return {v + o.v}; }
    bool operator==(Kilograms o) const { return v == o.v; }
    // ... и ещё 5-6 подобных операторов для каждой сущности
};
```

Если таких типов десятки, вы быстро получите сотни строк практически одинакового кода. На этом этапе легко допустить опечатку (например, забыть сменить возвращаемый тип при копировании оператора из одной структуры в другую), а объём сопутствующего кода начнёт обгонять саму логику. 

Эту рутину можно частично упростить, например, с помощью шаблонов (об этом в разделе «Инструменты оптимизации»). А пока рассмотрим еще одно преимущество разделения типов.

<a id="overloading-bonus"></a>
### Возможность перегрузки функций

Использование базовых типов — то самое проявление **Primitive Obsession** — лишает возможности использовать перегрузку и заставляет либо плодить громоздкие уникальные имена для каждой комбинации параметров, либо переходить к ветвлению во время исполнения:

```cpp
// Вариант БЕЗ сильных типов:
// Либо так (ветвление в рантайме):
double discount(double price, double value, bool is_percent);

// Либо так (уникальные имена для каждой комбинации):
double discount_by_percent(double price, double percent);
double discount_by_absolute(double price, double rubles);
```

Сильные типы предлагают третий путь: система типов сама выберет нужный алгоритм еще на этапе компиляции. Это позволяет избавиться от лишних флагов и ветвлений, передавая выбор нужной реализации компилятору:

```cpp
struct Price   { double value; };
struct Percent { double value; };
struct Rubles  { double value; };

// Разграничиваем логику скидок на уровне типов:
Price discount(Price p, Percent pct) {
    return Price{p.value * (1.0 - pct.value / 100.0)};
}

Price discount(Price p, Rubles off) {
    return Price{p.value - off.value};
}
```

<a id="flexible-order"></a>
### Гибкий порядок параметров

Еще один эффект перегрузки — возможность сделать порядок параметров неважным. Это спорный, но иногда дающий уникальное удобство интерфейса приём:

```cpp
Price discount(Price p, Rubles off) { return Price{p.value - off.value}; }
Price discount(Rubles off, Price p) { return discount(p, off); }

void test() {
    Price p{1000.0};
    auto p1 = discount(p, Rubles{150.0}); 
    auto p2 = discount(Rubles{150.0}, p); // Оба варианта работают одинаково прозрачно
}
```

**Границы применимости.** Этот метод идеально работает для двух параметров. При увеличении числа аргументов количество необходимых перегрузок растет факториально. Для сложных функций с 3–4 параметрами эффективнее переходить к паттерну Builder или передавать данные через структуры (именованные параметры). В задаче управления порядком сильные типы — это инструмент упрощения простых случаев.

<a id="rationality"></a>
## Не всё так просто: немного о практике

Как может выглядеть использование сильного типа в реальности? Выше был рассмотрен самый простой вариант со структурой и открытым полем. В новом, изолированном коде он вполне применим — когда вы полностью контролируете все точки вызова и уверены, что никто не подставит туда «сырое» число.

Однако в реальных проектах чаще приходится иметь дело с рефакторингом. У вас уже есть сотни функций и тысячи строк кода, которые нужно адаптировать. Именно здесь возникает самый сильный соблазн — сделать сильные типы «прозрачными», добавив оператор неявного приведения к базовому типу. Это кажется быстрым способом «просто заставить всё работать», но на практике такая уступка может свести на нет всю защиту.

Проблема в том, что при наличии старых версий функций компилятор не остановит вас ошибкой. Если он не найдет точного совпадения для сильных типов (например, из-за ошибки в порядке), то просто «тихо» приведет объекты к числам и вызовет старый вариант API. В итоге защита становится иллюзорной:

```cpp
// Предполагается, что Meters и Seconds получили НЕЯВНЫЙ operator double() 
// ради быстрого рефакторинга:

// 1. Старое API
constexpr double speed(double d, double t) { return d / t; }

// 2. Новое API (перегрузка для сильных типов)
constexpr double speed(Meters d, Seconds t) { return d.value / t.value; }

void test() {
    Meters d{100.0}; Seconds t{5.0};
    speed(d, t); // Выберется (2)
    speed(t, d); // Ошибка: Meters не приводится к Seconds, но оба приводятся к double.
                 // Компилятор выберет старый вариант (1). Ошибки сборки не будет.
}
```

Чтобы гарантировать защиту, необходим `explicit`. Это своего рода **цена за безопасность**: вместе с ним приходится прописывать и операторы для защиты логики, о которых говорилось выше. В сумме это всегда инфраструктурный код, и в масштабах проекта его объем может быть внушительным. В этой точке становится важно нащупать условия, при которых выбор в пользу сильных типов остается рациональным решением, а не превращается в избыточное усложнение. 

Выбор зависит от множества обстоятельств. Но можно выделить наиболее ясные случаи — например, «бизнес-ключи» (UserId, OrderId) или физические величины. Здесь данные представляют логически несовместимые сущности: использование UserId вместо OrderId лишено смысла и всегда ведет к ошибке. Именно в таких точках «говорящие» типы приносят максимум пользы, блокируя случайную подмену данных еще при сборке.

<a id="optimization"></a>
## Инструменты оптимизации

Понятно, что писать десятки одинаковых операторов вручную никто не будет — это перечеркивает всю пользу от инструмента. Но и отказываться от защиты не обязательно. На практике эту механическую работу просто поручают автоматике.

<a id="templates-simplification"></a>
### Уровень 1: Шаблоны (TypeWrapper)

Чтобы не прописывать операторы для каждой сущности вручную, логично вынести общую часть в шаблон. В самом простом виде он выглядит так:

```cpp
template <typename T, typename Tag>
struct TypeWrapper {
    T value;

    explicit constexpr TypeWrapper(T v) : value(v) {}
    explicit constexpr operator T() const { return value; }
};
```

На первый взгляд, анатомия этого шаблона элементарна:
1.  **Полезная нагрузка (`T value`)** — те самые данные (число), с которыми ведется работа.
2.  **Общая оболочка** — код самого шаблона, который задаёт правила поведения (конструкторы, операторы) один раз для всех.

Но здесь есть и третий элемент, который и делает всю схему рабочей: параметр **`Tag`**. 

В прикладном программировании тип обычно выступает контейнером для данных или поведения (поля, методы). Использование типов в шаблонах также предполагает наличие функциональной роли. Например, в `std::vector<int>` тип `int` определяет правила выделения памяти и копирования элементов, а в `std::map` — способы сравнения ключей.

В описываемом подходе используется пустая структура, не несущая данных и не влияющая на работу процессора. Тип применяется исключительно ради его **идентичности**, а не содержимого. Для компилятора `TypeWrapper<double, MetersTag>` и `TypeWrapper<double, SecondsTag>` — это две абсолютно разные, несовместимые вселенные, просто потому что у них разные **типы-теги**.

Такое использование типа как «маркера» или «имени» — одна из ключевых идей, которые лежат за границей привычного минимума. Это переход от программирования *данными* к программированию *информацией о типах*. Именно **уникальность** тега позволяет системе типов различать сущности с идентичным внутренним устройством. Создание нового типа сводится к объявлению пустой структуры-маркера, которая служит уникальным идентификатором для специализации шаблона.

Теперь создание нового типа сводится к объявлению тега и именованию уникальной специализации шаблона:

```cpp
struct MetersTag {};
using Meters = TypeWrapper<double, MetersTag>;

void func(Meters m) {
    // Безопасность есть, но удобства мало: нужен каст или .value
    std::cout << static_cast<double>(m) << " m" << std::endl;
}
```

Помимо автоматизации инфраструктуры, шаблонный подход дает удобный бонус — возможность «подключить» все типы к стандартной библиотеке одним блоком кода. Например, благодаря единому шаблону `TypeWrapper` проблему можно решить один раз для всех производных типов, просто специализировав `std::hash`:

```cpp
namespace std {
    template <typename T, typename Tag>
    struct hash<TypeWrapper<T, Tag>> {
        size_t operator()(const TypeWrapper<T, Tag>& w) const {
            return std::hash<T>{}(static_cast<T>(w));
        }
    };
}
```

Этот подход решает проблему создания типов, но оставляет решение половинчатым. Шаблон `TypeWrapper` взял на себя инфраструктурный код (конструкторы, хеши), но доменные правила (арифметика, сравнения) по-прежнему требуют ручного труда. 

Технически, шаблон `TypeWrapper` можно научить автоматически генерировать нужные операторы. Однако методы для такой автоматизации (Mixins, CRTP) еще не рассматривались, а разработка и поддержка собственного решения часто обходятся дороже, чем освоение готового инструмента. В таких случаях рациональнее не изобретать велосипед, а сразу обратиться к возможностям профессиональных библиотек.

<a id="libraries"></a>
### Уровень 2: Готовые библиотеки

Что делать, если типов становятся десятки? Прописывать вручную арифметику, сравнения и операторы вывода для каждой новой сущности — это путь к опечаткам и раздуванию кодовой базы. Здесь имеет смысл воспользоваться готовыми библиотеками (вроде [NamedType](https://github.com/joboccara/NamedType), [strong_type](https://github.com/rollbear/strong_type) или [type_safe](https://github.com/foonathan/type_safe)). 

Их главная задача — **автоматизировать создание «навыков» типа**. Вместо того чтобы кодить каждый оператор, вы декларативно собираете тип из готовых компонентов (Skills/Mixins), а библиотека сама генерирует всю необходимую обвязку «под капотом»:

```cpp
// Пример: тип 'Width' автоматически получает оператор + и поддержку std::cout
using Width = fluent::NamedType<
    double, struct WidthTag, fluent::Addable, fluent::Printable
>;

void test() {
    Width w1{10.0}, w2{20.0};
    auto total = w1 + w2; // Сгенерировано библиотекой автоматически
    std::cout << total;   // Сгенерировано библиотекой автоматически
}
```

<details>
  <summary>На что еще можно посмотреть (Библиотеки)</summary>
  <ul>
    <li><b>NamedType</b> — фокус на выразительности интерфейсов и «именованных параметрах».</li>
    <li><b>strong_type</b> — мощный инструментарий для сложной математики (разграничение векторов, точек и т. д.).</li>
    <li><b>type_safe</b> — для тех, кому важна максимальная строгость: запрет неявных потерь точности и переполнений.</li>
  </ul>
</details>

Использование библиотек сводит написание инфраструктурного кода к минимуму. Это делает применение сильных типов более доступным, хотя и требует освоения инструментария.

<a id="new-standards"></a>
## Инструменты современного C++ (C++11...C++23)

Насколько эти техники актуальны в эпоху «современного» C++? Под этим термином понимаются возможности, появившиеся начиная с переломного стандарта C++11. Стоит рассмотреть, как встроенные инструменты языка взаимодействуют с обертками и где они могут их заменять.

<a id="designated-initializers"></a>
### Явная инициализация агрегатов
В C++20 появились «designated initializers», позволяющие указывать имена полей при инициализации структур. Именованная инициализация снимает вопрос о том, какое значение к какому полю относится:

```cpp
struct Area {
    double width;
    double height;
};

Area a{ .width = 10.0, .height = 20.0 };
```

Такой синтаксис помогает в момент создания структуры, но он бессилен, если функции продолжают принимать «голые» типы. Однако Designated Initializers открывают путь к прагматичному компромиссу — паттерну **Parameter Object**. 

Если функция принимает несколько однотипных параметров (например, размеры и прозрачность окна), создание сильной обертки для каждого «числа» может перегрузить код. В этом случае прагматичным компромиссом становится объединение их в одну структуру-агрегат — паттерн **Parameter Object**.

Рассмотрим функцию настройки окна:

```cpp
struct WindowConfig {
    double width, height, opacity;
};

void create_window(WindowConfig config) {
    // Внутри функции это по-прежнему обычные double
}

// Вызов стал наглядным и безопасным:
create_window({
    .width = 800.0, 
    .height = 600.0, 
    .opacity = 0.9
});
```

Такой синтаксис гарантирует правильный порядок аргументов: в отличие от языка C, стандарт C++20 требует, чтобы последовательность инициализаторов строго совпадала с порядком полей в структуре, иначе код не скомпилируется.

Однако важно понимать: этот способ защищает только в момент вызова. Внутри самой функции поля структуры остаются обычными числами. Компилятор не помешает вам случайно вычесть время из расстояния, если вы ошибётесь в формуле. В этом и есть главное отличие от сильных типов: структура защищает порядок данных при передаче (call-site safety), но не их смысл при использовании (domain safety). 

Таким образом, Designated Initializers — отличное подспорье для простых структур, но они решают лишь часть проблем. Технически ничто не мешает совмещать их с сильными типами, однако делать структуру-агрегат, поля которой также являются обертками, чаще всего избыточно. Это становится оправданным лишь тогда, когда данные из структуры передаются дальше по системе и требуют защиты своего смысла за пределами этой функции. В противном случае нагромождение пяти структур-оберток ради одного контейнера лишь необоснованно усложнит код. 

<a id="udl"></a>
### Определяемые пользователем литералы

Определяемые пользователем литералы (UDL) органично дополняют концепцию сильных типов. Этот механизм позволяет превращать числовые константы в семантические объекты прямо в месте использования. По существу, литералы — это удобный синтаксический инструмент для конструирования сильных типов, избавляющий код от визуального шума конструкторов.

Инструмент можно встретить в стандартной библиотеке, например в `std::chrono`: суффикс `12h` превращает число в объект типа «часы» (hours). В пользовательском коде UDL имеют свои особенности. Имена пользовательских суффиксов обязаны начинаться с подчёркивания (суффиксы без него зарезервированы для стандарта). Кроме того, операторы литералов (`operator""`) принимают только ограниченный набор «сырых» типов: `unsigned long long` для целых чисел и `long double` для чисел с плавающей точкой. 

Несмотря на эти ограничения, эффект впечатляет:

```cpp
struct Meters  { double value; };
struct Seconds { double value; };

// Литералы для чисел с плавающей точкой (long double)
constexpr Meters  operator"" _m(long double x) { return Meters{static_cast<double>(x)}; }
constexpr Seconds operator"" _s(long double x) { return Seconds{static_cast<double>(x)}; }

// Литералы для целых чисел (unsigned long long)
constexpr Meters  operator"" _m(unsigned long long x) { return Meters{static_cast<double>(x)}; }
constexpr Seconds operator"" _s(unsigned long long x) { return Seconds{static_cast<double>(x)}; }

void test() {
    // Безопасно, лаконично и наглядно:
    auto dist = 10.0_m; // Meters через long double
    auto time = 5_s;    // Seconds через unsigned long long
    
    std::cout << speed(dist, time) << "\n";
}
```

Использование суффиксов `_m` и `_s` избавляет код от визуального шума конструкторов вроде `Meters{10.0}`, сохраняя при этом все преимущества сильных типов. Это отличный способ «сгладить углы» там, где смысл выражен через простые константы. Однако стоит помнить, что литералы хорошо справляются с простыми типами, но не рассчитаны на создание сложных объектов.

<a id="conclusion"></a>
## Оглядываясь назад: анатомия простых деталей

Сделан первый шаг от прикладного программирования к библиотечному. Важно было увидеть, что за пределами привычного минимума находятся не монолитные «магические» решения, а комбинация понятных элементов:

1.  **Шаблоны классов** (универсальный каркас) — отделение логики реализации от конкретной идентичности типа.
2.  **Перегрузка функций** (таблица решений) — выбор поведения еще на этапе компиляции.
3.  **Пустой тип** (маркер смысла) — простая, но важная идея, практически не имеющая накладных расходов в рантайме. К этой теме еще предстоит вернуться.

Из этого списка лишь пустые типы редко встречаются в повседневном прикладном коде. Однако именно понимание того, как все эти детали работают вместе, помогает перестать воспринимать подобные техники как нечто магическое. Разбор такой «анатомии» показывает: за любым сложным решением стоит комбинация простых элементов, которые в дальнейшем будут встречаться снова и снова.

В этой части речь шла о **сильных типах**, а пустые структуры-тэги выступали лишь как вспомогательный инструмент реализации. Однако в следующей части именно тэги выйдут на первый план. Речь пойдет о **Tag Dispatching** — технике, которая позволяет управлять самим ходом вычислений, выбирая нужные алгоритмы еще на этапе компиляции.
